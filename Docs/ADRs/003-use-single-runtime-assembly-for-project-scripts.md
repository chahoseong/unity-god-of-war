# 003: 프로젝트 스크립트 컴파일 관리를 위해 단일 런타임 어셈블리를 사용함

## 상태 (Status)

승인됨 (Accepted)

## 날짜 (Date)

2026-10-18

## 맥락(Context)

우리는 자체 개발 코드(`Assets/_Project/`)와 외부 서드파티 에셋(`Assets/Synty/`)을 명확히 구분하여 프로젝트를 구성하고 있다. 현재 Synty 에셋 패키지에는 샘플 코드와 툴(`PropBoneBinder` 등)을 포함해 16개의 C# 스크립트가 포함되어 있으나, 어셈블리 정의 파일(`.asmdef`)이 없어 모두 유니티의 기본 어셈블리인 `Assembly-CSharp`로 컴파일된다. 더욱이 `Assets/Synty/` 경로는 `.gitignore` 설정에 따라 버전 관리에서 제외되어 있으므로, 해당 폴더 내부에 어셈블리 설정을 추가하더라도 다른 개발 환경에 공유되지 않는다.

반면, 3인칭 근접 액션 전투에는 선입력 버퍼링(Input Buffering)이나 후딜레이 캔슬(Cancel Window)처럼 타이밍에 매우 민감한 전투 규칙들이 존재하며, 이러한 규칙들은 신속하고 안정적인 개발을 위해 무거운 씬(Scene) 실행 없이도 자동화 테스트를 붙여 지속적으로 검증할 수 있어야 한다. 그러나 유니티의 어셈블리 참조 규칙상 테스트 어셈블리는 `Assembly-CSharp`를 직접 참조할 수 없다. 따라서 게임 코드에 자동화 테스트를 구축하기 위해서는 자체 코드가 별도의 어셈블리로 분리되어야 한다.

동시에 게임 규칙상 핵심 전투 기능들은 다음과 같이 서로 밀접하게 맞물려 있다:
- **공격 판정과 방어 상태**: 공격의 최종 결과(일반 피격, 가드 성공, 가드 브레이크, 저스트 패링)는 피격 대상의 가드 입력 타이밍에 달려 있다.
- **캐릭터 이동과 카메라**: 8방향 스트레이프 이동은 카메라의 정면 방향을 기준으로 연산되며, 카메라는 캐릭터의 이동을 따라가고 락온(Lock-On) 대상을 추적한다.
- **전투 피드백의 동시 적용**: 타격 순간에는 공격자와 피격자에게 적용되는 역경직(Hitstop)과 화면 전체에 적용되는 카메라 쉐이크(Camera Shake)가 동시에 발동된다.

어셈블리 간의 참조는 반드시 한 방향으로만 흘러야 하므로, 이 맞물린 기능들을 개별 어셈블리로 쪼갤 경우 기능 간의 의존 방향을 어셈블리 경계로 고정해야 하는 구조적 제약이 발생한다. 따라서 자동화 테스트 환경을 확보하면서도 기능 간의 유연한 협업을 지원하기 위한 컴파일 경계 설계가 요구된다.

선택할 수 있는 옵션으로는 Assembly Definition을 사용하지 않는 방식, 단일 런타임 어셈블리로 구성하고 에디터·테스트 코드만 분리하는 방식, 또는 기능 영역별로 어셈블리를 세분화하는 방식이 있다.

## 결정(Decision)

**우리는 프로젝트의 런타임 스크립트를 단일 어셈블리(`GodOfWar.Runtime`)로 구성하고, 에디터 코드와 테스트 코드는 별도 어셈블리로 분리한다.**

폴더 이름은 유니티 패키지 레이아웃 관례(`Runtime/`, `Editor/`, `Tests/`)를 따르며, 각 어셈블리의 위치와 역할은 다음과 같다:

| 어셈블리 | 위치 | 역할 |
|---|---|---|
| `GodOfWar.Runtime` | `Assets/_Project/Scripts/Runtime/` | 게임 런타임 코드 |
| `GodOfWar.Editor` | `Assets/_Project/Scripts/Editor/` | 에디터 전용 코드 |
| `GodOfWar.Tests.Editor` | `Assets/_Project/Scripts/Tests/Editor/` | EditMode 테스트 |
| `GodOfWar.Tests.Runtime` | `Assets/_Project/Scripts/Tests/Runtime/` | PlayMode 테스트 |

`GodOfWar.Runtime`은 `autoReferenced` 옵션을 `false`로 설정하여, `Assembly-CSharp`나 외부 스크립트가 우리 게임 타입을 무분별하게 자동으로 참조하는 것을 방지한다. 또한 패키지 참조는 실제로 사용하는 것만 최소한으로 연결합니다.

이러한 결정을 내린 이유는 서드파티 코드와 컴파일 경계를 만들고 자동화 테스트를 붙일 수 있게 하면서도, 게임 규칙상 서로 맞물린 전투 기능들 사이의 의존 방향이 어셈블리 구성에 묶이지 않도록 유연성을 확보하기 위함이다.

## 대안(Alternatives)

- **A. Assembly Definition 미사용**
  - **장점**: 별도의 어셈블리 정의 파일 설정 없이 바로 스크립트를 작성할 수 있다.
  - **단점**: 서드파티 에셋(Synty)의 샘플 코드와 같은 어셈블리에 섞여 코드 경계가 사라진다. 유니티 어셈블리 참조 규칙상 테스트 어셈블리가 `Assembly-CSharp`를 참조할 수 없어 자동화 테스트를 붙일 수 없다.
- **B. 단일 런타임 + 에디터·테스트 분리 (채택)**
  - **장점**: 관리할 설정이 최소화되면서 서드파티 코드와 격리되고 자동화 테스트가 가능해진다. 핵심 기능 간의 의존 방향이 어셈블리 구성에 묶이지 않아 구현 및 변경이 자유롭다.
  - **단점**: 런타임 내부 세부 폴더 간의 의존 방향을 컴파일러 차원에서 강제하지 못한다.
- **C. 기능별 분리 (Core / Input / Character / Combat / Camera / AI)**
  - **장점**: 기능 모듈 간의 의존 방향을 컴파일 타임에 강제할 수 있으며, 변경된 어셈블리만 다시 컴파일할 수 있다.
  - **단점**: 어셈블리 간 참조는 한 방향이어야 하므로, 규칙상 서로 맞물린 기능들 사이의 의존 방향을 어셈블리 경계로 고정해야 한다. 개발 진행 중 의존 방향이 바뀌면 어셈블리 구성 전체를 수정해야 하며, 버티컬 슬라이스 규모에서는 구조적 오버헤드에 비해 컴파일 시간 이득이 작다.

## 결과(Consequences)

우리 프로젝트의 코드가 서드파티(Synty) 코드와 분리된 독립 어셈블리로 컴파일되므로, 타이밍에 민감한 전투 로직을 포함한 게임 코드 전반에 EditMode 및 PlayMode 자동화 테스트를 자유롭게 붙여 검증할 수 있다. 또한 `autoReferenced: false` 설정 덕분에 `Scripts/Runtime/` 외부 경로에 놓인 스크립트가 게임 타입을 무단 참조하면 컴파일 에러가 발생하여 안전한 경계가 유지된다.

반면 단일 런타임 구조에서는 어셈블리 내부 폴더 간의 의존 방향을 컴파일러가 강제하지 못한다. 이를 보완하기 위해 다음 규칙을 `AGENTS.md`에 명시하고 준수한다:
- `Core/` 안의 코드는 `GodOfWar.Core.*` 외의 `GodOfWar.*` 네임스페이스를 참조하지 않는다.

또한 유니티의 어셈블리는 `Assembly-CSharp`를 참조할 수 없으므로, Synty 스크립트(`PropBoneBinder` 등)는 프리팹 컴포넌트로만 활용할 수 있고 우리 코드에서 타입으로 직접 참조할 수 없다. 아울러 Assembly Definition이 포함된 폴더 안에서는 유니티의 `Editor` 특수 폴더 규칙이 적용되지 않으므로, 에디터 전용 코드는 반드시 `Scripts/Editor/`에 분리하여 배치해야 한다.
