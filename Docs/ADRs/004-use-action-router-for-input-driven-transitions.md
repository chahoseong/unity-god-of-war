# 004: 입력 기반 상태 전이(Input-Driven Transition) 제어를 위해 행동 라우터(Action Router)를 사용함

## 상태 (Status)

승인됨 (Accepted)

## 날짜 (Date)

2026-10-22

## 맥락(Context)

우리는 ADR-001에서 캐릭터 행동 상태를 제어하기 위해 모듈형 유한 상태 머신(Modular FSM)을 채택했다. 이에 따라 이동, 회피, 공격, 가드 등 각 행동이 독립된 상태(State) 클래스로 분리되었으나, 플레이어 입력에 따른 상태 간 전이(State Transition)를 어떻게 중재하고 결정할 것인가에 대한 구체적인 구조가 필요하다.

3인칭 근접 액션 전투에서는 다음과 같은 엄격하고 복잡한 입력 전이 규칙을 처리해야 한다:
- **후딜레이 캔슬(Cancel Window)**: 공격 중 후딜레이 캔슬 구간에서 회피나 가드 입력이 들어오면 현재 동작을 취소하고 해당 행동으로 즉시 전이해야 한다.
- **이동 조기 복귀(Early Exit)**: 공격 연계 구간이 끝난 뒤 이동 스틱이 밀려 있으면, 자세 복귀(Recovery) 클립을 끝까지 재생하지 않고 이동(`Locomotion`) 상태로 즉시 복귀하여 조작 반응성을 확보해야 한다.
- **상태 내부 연계(Combo & Sequence)**: 공격 진행 중 동일한 공격 버튼을 누르면 다음 콤보 타수를 실행하고, 퀵스텝 중 회피 버튼을 다시 누르면 2단 구르기(Roll)로 연계해야 한다.
- **우선순위 역전**: 다음 타수가 예약된 상태에서 회피를 입력한 경우, 회피가 우선되어 공격 예약을 끊고 즉각적인 생존 행동으로 이어져야 한다.
- **선입력 버퍼링(Input Buffering)**: 현재 행동이 끝나거나 캔슬 가능 시점에 도달하기 직전에 입력된 버튼 조작을 유실하지 않고 기억해 두었다가 적시에 실행해야 한다.

만약 각 상태 클래스가 캔슬 대상 상태를 직접 참조하여 전이하면, 예를 들어 `AttackState`가 `QuickStepState`, `GuardState` 등을 직접 참조하게 되어 상태 간 결합도(Coupling)가 급격히 증가한다. 또한 "스틱 방향이 있어야 회피 가능"과 같은 시작 조건을 발신 상태와 수신 상태 양쪽에서 중복 검사하는 등 진입 로직이 여러 코드에 분산되는 문제가 발생한다. 반대로 (현재 상태, 입력) 조합을 거대한 2차원 매트릭스 표로 관리하면 새로운 상태가 추가될 때마다 모든 상태 간의 전이 행렬을 갱신해야 하는 관리 비용이 발생한다.

따라서 입력 기반 전이에서 상태 간의 직접 참조를 제거하고, 진입 조건의 단일 진실 공급원(SSOT)과 선입력 버퍼링을 안정되게 확립할 수 있는 중앙 중재 구조가 필요하다.

## 결정(Decision)

**우리는 플레이어 입력에 따른 상태 전이를 중재하고 제어하기 위해 플레이어 전용 컴포넌트인 행동 라우터(Action Router)를 사용한다.**

행동 라우터는 플레이어의 단발성 버튼 입력(공격, 회피, 가드 등)을 수신하여 대상 상태를 결정하는 컴포넌트이다. 이때 라우팅 규칙을 중앙에 하드코딩하지 않고 각 상태가 자신의 진입 트리거를 직접 선언하며, 개별 상태는 구체적인 전이 대상을 알지 못한 채 오직 현재 시점에 다른 액션의 끼어들기를 허용하는지(캔슬 윈도우 개폐 여부)만을 응답한다.

상세 결정 사항은 다음과 같다:

### 1. 라우터의 역할과 상태의 진입 선언 (Self-Registration)
- **분산형 자기 선언**: 라우팅 규칙을 중앙 코드(`PlayerController` 등)에 정적으로 모아 적지 않고, **각 상태 클래스가 자신의 진입 트리거`(입력, 시작 조건, 우선순위)`를 스스로 선언**한다.
  - 예: `QuickStepState`는 "Dodge 입력 + 스틱 방향 유효 조건", `AttackState`는 "공격 입력"을 스스로 선언한다.
- **동적 라우팅 테이블 구축**: 라우터는 초기화(상태 등록) 시점에 각 상태가 선언한 진입 규칙을 수집(Aggregate)하여 내부 라우팅 테이블을 자동으로 구축한다. 라우팅 테이블은 `(입력, 대상 상태, 시작 조건, 우선순위)`로 구성되며, 테이블 내에 "현재 상태" 열은 두지 않는다.
- **진입 조건의 단일 진실 공급원(SSOT)**: 상태의 시작 조건(예: 스틱 방향 유효성)을 해당 상태가 온전히 소유하므로, 여러 상태에 걸친 조건의 중복 검사와 로직 분산을 원천 차단한다.
- **동일 입력 경합 시 판정 순서 및 Fail-Fast**: 동일한 입력을 여러 상태가 선언하는 경우(예: 일반 공격과 스턴 처형기가 모두 공격 버튼을 공유), **시작 조건을 만족하는 상태들 가운데 우선순위가 가장 높은 상태로 전이**한다.
  - 같은 입력을 선언한 상태들 사이에서 우선순위가 중복되면 등록 시점에 즉시 에러를 발생시켜(Fail-Fast) 런타임 오동작을 사전에 차단한다.
- **상태 간 결합도 분리(Decoupling)**: 현재 상태는 입력 캔슬로 넘어갈 대상 상태를 알지 못한다 (예: `AttackState` 코드 내에 `QuickStepState`나 `GuardState`에 대한 참조가 전혀 없음). 현재 상태는 라우터에 캔슬 윈도우의 개폐 여부만 제공한다.

### 2. 제어 범위: 버튼 입력으로 한정 및 이동의 제외
- **버튼 입력으로 범위 한정**: 행동 라우터는 단발성 버튼 입력(공격, 회피, 가드 등)만 전담한다. 이동 스틱에 의한 이동은 라우터의 제어 범위에서 제외하고, 각 행동 상태의 자연스러운 종료(조기 복귀) 전이로 처리한다.
- **이동을 제외하는 이유**:
  - 공격 후 이동은 다른 행동이 끼어드는 선점(Cancel)이라기보다, **공격을 언제 마무리할지(Early Exit)**의 문제이다.
  - 이동 가능 시점(연계 구간 종료 후, 다음 타 미예약)은 모두 `AttackState` 내부 타이밍이므로 상태가 직접 판단하는 것이 내부 상태를 밖으로 노출하지 않고 캡슐화하기에 적합하다.
  - 매 프레임 판정해야 하는 연속 유지 입력을 배제함으로써, 라우터가 단순한 이벤트 디스패처로 유지되며 "대상이 현재 상태와 같으면 무시한다" 같은 예외 규칙도 완전히 불필요해진다.
- **따라오는 규칙 (조기 복귀 조건)**: 이동으로 일찍 복귀해야 하는 상태(`AttackState` 등)는 기존의 `Locomotion` 복귀 로직에 *"연계 구간 종료 후 이동 스틱이 밀려 있으면 복귀 모션을 끝까지 재생하지 않고 즉시 `Locomotion`으로 전이"*하는 조기 종료 조건을 포함한다.

### 3. 상태와 라우터의 약속 (Protocol)
- **상태의 양방향 계약**: 상태는 라우터와 두 가지 계약을 맺으며, 이를 통해 자신의 진입 조건과 끼어들기 허용 시점을 스스로 소유한다:
  1. **진입 계약 (Inbound)**: "나는 어떤 입력, 시작 조건, 우선순위로 시작되는가" (결정 1)
  2. **캔슬 허용 계약 (Outbound)**: "나는 지금 다른 액션의 끼어들기(캔슬)를 허용하는 구간인가 (`IsCancelWindowOpen: true/false`)?"
- **단일 캔슬 윈도우(Cancel Window) 채택**: 각 상태는 판정 시점에 다른 액션을 받아 줄 수 있는지 여부를 단일 불리언 프로퍼티로 응답한다.
  - 행동 종류별 체크리스트를 두면 새 행동(가드 등)이 추가될 때마다 이를 허용해야 하는 기존 상태 파일들을 일일이 수정해야 하는 파급 수정(Ripple Effect)이 발생한다.
  - 현재 전투 시스템은 특정 타이밍의 개폐(선딜 구간 닫힘, 후딜레이 캔슬 구간 열림)만으로 충분하므로, 단일 캔슬 윈도우로 단순화하여 새 상태 추가 시 **기존 상태 파일의 무수정(OCP)**을 온전히 보장한다.
- **묵시적 기본값 배제 (Fail-Fast 정책)**: 시스템 안정성을 위해 '선언이 없으면 캔슬 상시 허용/상시 거절'과 같은 묵시적 기본값을 두지 않는다.
  - 모든 플레이어 상태는 캔슬 윈도우 프로퍼티를 명시적으로 선언해야 하며, 선언 누락은 컴파일 시점에 즉시 감지되어야 한다. 이를 통해 실수를 런타임이 아닌 컴파일 시점에 드러내고, 상태 파일 상단에서 정책을 명확히 파악할 수 있도록 한다.
  - ADR-003(Core 독립성)에 따라 도메인 중립적인 Core 어셈블리의 `IState`를 오염시키지 않고, 이 선언 의무는 플레이어 도메인 경계 안에서 강제한다 (행동 라우터 역시 플레이어 전용 컴포넌트이다).

### 4. 입력 처리 흐름 및 우선순위 (Priority & Buffering)
- **상태 내부 연계 우선 질의**: 입력이 들어왔을 때, 라우터는 라우팅 테이블을 조회하기 전에 먼저 현재 상태에 해당 입력이 내부 연계(공격 콤보 다음 타수, 퀵스텝 중 구르기 연계 등)에 해당하는지 질의(Query)한다.
  - 상태가 처리하지 않은 경우에만 라우터 표의 전이 규칙으로 넘어간다.
  - 이 처리 흐름 덕분에 맥락 절에서 언급한 '우선순위 역전' 요구사항이 자연스럽게 성립한다. 회피는 공격 상태의 후속 행동이 아니므로 상태가 거절하여 라우터 표로 넘어가고, 후딜레이 구간에서 캔슬 윈도우가 열려 있어 회피 상태로 전이되며, 이때 공격 상태를 빠져나오면서 예약된 다음 타는 소멸하기 때문이다.
- **실제 처리 시에만 처리 완료 반환**: 상태는 실제로 콤보나 연계를 이어 갔을 때만 `Handled: true`를 반환한다.
  - 상태가 거절한 입력은 라우터에 그대로 남게 되므로, 선입력 버퍼링(Input Buffering)을 라우터에 일원화하여 관리할 수 있다.

### 5. 강제 상태 전이와의 경계 분리
- **입력 전이와 강제 전이의 분리**: 피격, 가드 브레이크, 스턴, 사망 같은 외적 전이는 라우터 밖에서 전투 시스템이 FSM을 통해 직접 처리한다.
  - 라우터의 범위를 플레이어 입력으로 한정하여, 피격 판정, 슈퍼아머, 가드/패링 판정 등의 전투 도메인 로직이 라우터와 섞이지 않도록 방지한다.
- **입력 버퍼 비우기(Flush)**: 강제 전이가 발생하면 라우터가 기억하던 선입력 버퍼를 즉시 비워, 피격 후 의도치 않은 조작이 지연 발동되는 문제를 방지한다.

## 대안(Alternatives)

- **A. 상태 간 직접 전이 (State-to-State Direct Transition)**
  - **장점**: 별도의 라우터나 중재 컴포넌트 없이 각 상태에서 즉시 다른 상태로 전환할 수 있어 초기에 빠르게 작성할 수 있다.
  - **단점**: 상태 간 양방향 결합도(Coupling)가 증가하여 `AttackState`가 `QuickStepState`, `GuardState` 등을 직접 알아야 하며, 공격 후딜레이 캔슬 판정과 선입력 버퍼링 로직이 상태마다 중복 구현된다.
- **B. 중앙 집중형 전이 행렬 / 정적 테이블 (Centralized Transition Matrix / Table)**
  - **장점**: 전체 상태 전이 조합이나 라우팅 표를 한 파일(`PlayerController` 등)에서 한눈에 조감할 수 있다.
  - **단점**: 새로운 액션 상태를 추가할 때마다 중앙 표나 행렬 코드를 반드시 수정해야 하므로 OCP(개방-폐쇄 원칙)가 저해되며, "스틱 방향 유효성" 같은 시작 조건 검사 로직이 중앙 표와 상태 클래스로 분산되거나 중복 검사된다.
- **C. 상태 자기 선언 기반 행동 라우터 (Self-Registering Action Router with Cancel Window) [채택]**
  - **장점**: 입력 기반 전이에서 상태 간의 직접 참조가 완전히 제거되며, 새 액션 추가 시 기존 라우터나 상태 코드를 건드리지 않고 새 상태 파일 작성과 등록 한 줄만으로 완결된다. 또한 캔슬 타이밍 판정(단일 캔슬 윈도우)과 선입력 버퍼링이 중앙에서 단순하고 안정적으로 일원화된다.
  - **단점**: 전체 전이 목록이 상태 파일마다 분산되어 가시성이 낮아지므로(초기화 로그 덤프로 보완 필요), 동일한 입력을 공유하는 상태 간에는 명시적인 우선순위 선언과 충돌 방지 규칙이 요구된다.

## 결과(Consequences)

각 상태가 자신의 진입 트리거와 시작 조건을 직접 선언하고 라우터가 이를 수집하므로, 새로운 액션 상태를 추가할 때 기존 라우터 코드를 수정하지 않고 새 상태 파일 작성과 컨트롤러 등록 한 줄만으로 완결되는 완전한 파일 격리성(ADR-001 연계, AI 협업 최적화)을 달성한다. 특히 단일 캔슬 윈도우를 채택함으로써 새 액션이 추가되어도 기존 상태 파일들을 건드릴 필요가 전혀 없다. 또한 시작 조건이 상태 내부로 캡슐화되어 진입 조건의 중복 검사 문제가 완전히 해소되며, 라우터가 다루는 입력을 단발성 버튼으로 한정하여 선입력 버퍼링(Input Buffering)을 단순하고 안정적인 버튼 큐 형태로 라우터에 일원화할 수 있다.

반면 전체 전이 목록이 상태 파일마다 분산되므로, 초기화 시점에 수집된 라우팅 테이블을 콘솔 로그나 인스펙터로 덤프하여 가시성을 확보해야 한다. 또한 동일한 입력을 공유하는 상태가 있을 경우 우선순위를 반드시 선언해야 하며, 등록 시점 충돌 에러(Fail-Fast) 규칙을 준수해야 한다. 그 외에 행동 종료 후의 자연 복귀(`AttackState`나 `QuickStepState`가 끝난 뒤 `LocomotionState`로 복귀)나 동일 계열의 후속 연계(`QuickStepState`에서 `DodgeRollState` 연계)에는 여전히 상태 간 참조가 남는다.

또한 현재의 단일 캔슬 윈도우는 액션 간 캔슬 타이밍을 동일하게 취급하므로 유효하다. 향후 전투 시스템의 진화로 인해 '특정 구간에서는 회피만 허용하고 가드는 차단'과 같이 행동 종류별 차등 허용이 요구될 경우, 캔슬 윈도우를 행동 종류별 필터로 확장해야 하며 이때는 기존 상태 코드의 파급 수정이 발생할 수 있다.
